## ADR-001 — Authorize admins via the `admins` table

- **Context**: Supabase Auth authenticates anyone with a valid email magic link. Authentication ≠ authorization — we must only let vetted committee members into the admin area, and distinguish Super vs Executive admins.
- **Decision**: After `getUser()`, look up the user in `public.admins` by `auth_user_id` with `active = true`. No matching active row → sign out + redirect to login. Role and per-capability `permissions` (jsonb) come from that row. Implemented in `admin/admin.js` `checkAdminAccess()`.
- **Reason**: Decouples "can log in" from "is an admin", lets us revoke access (`active = false`) without touching auth, and carries role/permissions in our own data.
- **Trade-off**: The client-side check is bypassable by anyone who can call the anon API directly — it is NOT a security boundary on its own. Postgres RLS is still required and currently missing (tracked as a known gap in `db-conventions.md` D6).
- **Supersedes / superseded by**: none
